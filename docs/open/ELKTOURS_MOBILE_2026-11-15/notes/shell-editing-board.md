### B3. Block model (packages/blocks) and what makes a block Puck-friendly
- A block = `defineBlock({id, category, label, description, props, memberSafe, styling:"tokens", resize?, parts?}, Component, sampleProps)` from `@elkdonis/blocks` (`packages/blocks/src/registry.ts`). `props` is a `PropDef[]` (name, kind: string|text|richtext|number|boolean|select|list|url|image|slot|rows, label, default, `inlineEditable`, `binds`). One declaration drives the Puck fields, direct-edit inline text, and server draw (`buildPuckConfig` in `packages/page-builder/src/config.tsx`).
- `parts` = `{ name: { label, sel, prop?, draws? } }`: CSS selectors over the block's real markup. Data only, no markup change. A part with `prop` gets inline-editable words in direct-edit; a part without `prop` can only get a look (colour, size, spacing) via `morph`, stored on the node. `draws: { props }` tells the editor what sample props make an optional part appear.
- `styling: "tokens"` means the block's look reads `--blk-*` custom properties (declared in `packages/blocks/src/blocks.css`, mapped from `--eac-block-*` in elktours globals.css lines ~50-65). So Site style or a part look can change it.
- Registered via `E/lib/puck/catalogue.ts` (`PAGE_BLOCKS`), which feeds `config.client.ts` (canvas + Studio) and `config.server.ts` (published draw). Add the new block there, in the three lists, and nothing else.

### B5. Site style (the "look" lever)
- Schema in code: `E/lib/site-style-schema.ts` (`SITE_STYLE`). Declared CSS vars an owner can edit: `--background` (also applied to `body{background}`), `--foreground`, `--muted-foreground`, `--card`, `--primary` (Brass), `--primary-foreground`, `--border`, `--eac-block-band`, `--site-font-body` (→ `body{font-family}`), `--site-font-heading` (→ `h1,h2,h3,h4,.font-serif`), `--radius`. Font choices: Basteleur, Brothers, Venture, Georgia, system sans, plus four Google fonts. Chrome parts: header (`brand city links active account menu`) and footer (`title note small links`), keyed by `data-chrome` + `data-part`.
- Storage: theme → `site_themes` (page_key ''), chrome → site_config `site-style:chrome` (`E/lib/site-style.ts`). Applied server-side in `layout.tsx` as `<style data-site-style>`; editor opens from `SiteStyleButton` (bottom-right, editors only), loads `@elkdonis/direct-edit/site/editor` lazily, previews live, saves via `saveSiteStyleAction`.
- `?site-style=1`: NOT found in elktours source (grep of `E/app` and `packages/direct-edit/src` for `site-style=1` gives nothing). Only the button opens the editor. Probably a hidden-enneagram/channel convention (`packages/studio/src/channel/nav.ts` has a `siteStyle` link). Flag for the owner of the brief.
- So yes: site style feeds CSS variables, and new components MUST read them. Rules:
  1. Colour: `hsl(var(--primary))`, `--card`, `--foreground`, `--muted-foreground`, `--background`, `--border`, `--popover`, `--secondary`, `--terracotta`, `--brass-light`. Tailwind aliases (`bg-primary`, `text-foreground`, ...) resolve to the same variables.
  2. Fonts: `font-serif`, `font-sans`, `font-mono` or `var(--site-font-body|heading)`, not literal `"Brothers"`. Caveat: Site style only re-targets `body`, headings and `.font-serif`; Venture kicker (`font-mono`) is not covered by a Site style var. Add `--site-font-kicker` to the schema if wanted.
  3. Corners: `--radius` is global and the pack wants fixed 20/30px radii. Use new `--radius-card/sheet/input` vars (A4) and add them to `SITE_STYLE.vars` (kind `length`) so the owner can still tune them. Do not bind them to `--radius`, which is 0 for desktop.
  4. Any NEW token the mobile redesign adds (verdigris, faint, hairlines, brass-line, scrim) only flows through to "look" edits if it is added to `SITE_STYLE.vars` (it lists only 11 today). Cheap: derive new ones from existing ones in CSS (`hsl(var(--foreground)/.12)`) so they follow automatically; list only genuinely independent ones (verdigris) in the schema.
  5. Header/footer parts: the mobile bottom nav should expose `data-chrome="nav"` and `data-part` names (`bar`, `item`, `active`, `badge`) and add `chrome.nav` to `SITE_STYLE` so the owner can restyle it like the header. Without that the new nav is outside Site style.
- Per-block look edits (parts + `morph`) go through `MorphMark` and are stored on the Puck node; they only work on blocks inside Puck pages (systems 1 and 2).

### B6. Recipe: building a NEW mobile component so it is Puck-prop friendly and direct-edit editable
(From `docs/open/EDITING_LANDSCAPE_2026-11-12/detail.md` section 4 "surface recipe" and `HANDOVER_TEAM_2026-11-14.md`.)
1. Decide the class. Marketing/guest content that the owner words and looks (Discover intro lines, Tours intro, About, section headers, hero, tour/experience page blocks) = class a: a `defineBlock` with `props` and `parts`. Tool UI (board, forms, nav logic) = class c (plain React), not in Puck.
2. Write the block in `E/blocks/...` or, if it is shared across sites, `packages/blocks/src/blocks/`. Use `defineBlock` (copy `hero-banner.tsx`): props with `label`, `default`, `inlineEditable: true` for every word the owner may change; `kind: "image"` for pictures; `richtext` for paragraphs (render via `RichText` from `@elkdonis/blocks`, which sanitises); `select`/`boolean` for variants (arched vs porthole frame, show/hide).
3. Markup: one root element (`<section className="blk blk-xxx">`) so a look reaches inside; give every editable bit a stable class (`.blk-xxx-title`). Do NOT add `data-part` attrs on public pages (the recipe avoids changing visitor HTML), use class selectors.
4. Declare `parts` over those classes: `root` first; give `prop:` to own-label words only (title, subtitle, kicker, button label). Never `prop` data words (tour titles, prices, dates from the DB): those stay locked and are edited in `/manage` forms.
5. Style with tokens only: read `--blk-*` or the shadcn vars (A2) with `styling: "tokens"`; no hex, no literal font names (B5).
6. Put markup that needs the viewer or DB data behind a resolver: `buildPuckConfig({ resolvers })` (see `E/lib/puck/config.server.ts`) for the published draw and the matching client resolver in `config.client.ts`, via a server action. Strip resolved keys on save (`E/lib/puck/resolved.ts` / RESOLVED_KEYS).
7. Records (a tour card, a place): draw with a shared face and give the block a `binds` prop ("From what?" chooser, `E/components/landing/person-records.ts` records, `mountRecordChooser`). Click opens a surface (`useSurface().open({kind})`, registered in `E/components/hub/HubSurfaces.tsx`); mark the block `interactive` and wrap in `EnsureSurface` so the editor cannot crash.
8. Register: add it to `PAGE_BLOCKS` in `E/lib/puck/catalogue.ts` (and the `SHARED_IDS` set if it comes from the shared package). That automatically gives it a Puck palette entry in `/studio/<slug>` and the landing canvas, and direct-edit inline words and "Edit look".
9. Tour and experience page blocks (`E/blocks/tour/*`, `E/blocks/experience/*`) use a different, older hand-rolled config with no `parts`. To make them look-editable, convert them to `defineBlock` with parts, or at minimum keep them token-driven. This is the biggest gap for "after redesign the editor can still change look".
10. Verify with the harness (`packages/direct-edit/harness/frankenstein/`) in a throwaway container; no rebuild without Justin's yes.

Rule of thumb for the redesign: each pack screen is either (i) a PAGE (Discover, Tours, About, intro lines) = blocks in Puck pages so copy and look stay editable; (ii) a RECORD VIEW (tour detail, experience, artist, place sheet) = existing tour/experience block layouts, restyled by tokens, with the new hero as a block; (iii) TOOL UI (everything in B screens 30-41, forms, wizard) = plain React, restyled, not in Puck.
